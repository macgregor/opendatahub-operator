## Executive Summary

**Stack:** Go 1.24.4 Kubernetes Operator (Kubebuilder v4) with OLM bundles, FIPS-compliant container images, GitHub Actions CI/CD

**Current State:** Basic security practices in place (golangci-lint, kube-linter, non-root containers, RBAC), but missing modern supply chain security, comprehensive vulnerability scanning, and SBOM generation.

**Gap:** No container image scanning, no SAST beyond linters, no automated dependency updates, no SBOM artifacts, no security policy enforcement in CI.

---

## Part 1: Traditional Security Toolbox

### 1.1 Static Application Security Testing (SAST)

**Add gosec** - Go-specific security scanner
- Detects: hard-coded credentials, weak crypto, SQL injection patterns, path traversal, command injection
- Integration: Add make target `make security-scan` + GitHub Actions workflow
- Config: `.gosec.json` with CWE mapping, SARIF output for GitHub Security tab
- Baseline: Generate and commit baseline to track new issues only

**Upgrade to GitHub Advanced Security (if available)**
- Enable CodeQL for Go (improved 2025 coverage)
- Supports private Go module scanning
- SARIF integration with existing gosec results

### 1.2 Container & Dependency Scanning

**Trivy** (primary scanner)
- Scan images: operator, bundle, catalog, toolbox
- Coverage: OS packages (UBI9), Go modules, config files, secrets
- Integration points:
  - Local: `make scan-images`
  - CI: Scan on PR builds before push to Quay.io
  - Runtime: Scan manifests with `trivy config`
- Output: SARIF for GitHub, JSON for artifacts
- Policy: Block HIGH/CRITICAL CVEs on main branch

**Syft + Grype** (SBOM + precision scanning)
- Syft generates CycloneDX/SPDX SBOMs for all images
- Grype performs vulnerability matching with lower false positives
- Attach SBOMs to GitHub releases and OLM bundles
- Enables downstream compliance requirements

### 1.3 Dependency Management

**Dependabot** (GitHub native)
- Enable for Go modules, GitHub Actions
- Group updates by type (security vs. non-security)
- Auto-merge patch versions after CI passes

**Go module security**
- Extend `Makefile` to include `go list -m -json all | go-mod-outdated` checks
- Add `make deps-check` target for manual audits
- Document excluded versions in go.mod (already present, formalize)

### 1.4 Supply Chain Security

**SBOM Generation Pipeline**
```
Build → Syft SBOM → Attach to release → Sign with Cosign → Verify in deployment
```

**Provenance & Signing** (SLSA compliance)
- Use GitHub OIDC + Sigstore Cosign for keyless signing
- Sign operator images and bundles
- Generate SLSA provenance attestations
- Store in Quay.io as OCI artifacts

**Dependency Review**
- Enable GitHub Dependency Review Action
- Block PRs introducing known vulnerabilities
- Review license compliance (Apache-2.0 compatibility)

### 1.5 Kubernetes Security Posture

**Enhance kube-linter** (already in use)
- Add custom rules for operator-specific patterns
- Enforce security contexts across all deployed components
- Validate RBAC least-privilege

**OPA/Gatekeeper policies** (optional, for testing)
- Define admission policies for local testing
- Mirror production RHACS policies in dev

### 1.6 Secrets Management

**Gitleaks** - Prevent credential leaks
- Scan commits for secrets before push
- Pre-commit hook + CI enforcement
- Baseline existing repo, monitor new commits

**TruffleHog** (alternative/complement)
- Deeper entropy analysis
- Historical commit scanning

### 1.7 Developer Workflow Integration

**Makefile targets** (unified interface)
```makefile
make security         # Run all security checks
make security-scan    # gosec + go vet security checks
make scan-images      # Trivy container scans
make sbom-generate    # Create SBOMs for all artifacts
make secrets-check    # Gitleaks scan
make deps-audit       # Go module vulnerability check
```

**Pre-commit hooks** (optional, developer choice)
- gosec on changed .go files
- gitleaks on staged changes
- Local Trivy scans before image push

**CI/CD Pipeline Architecture**
```
PR Event
├─ Lint (golangci-lint, kube-linter)
├─ SAST (gosec, CodeQL)
├─ Unit Tests + Coverage
├─ Build Images
├─ Scan Images (Trivy, Grype)
├─ SBOM Generation (Syft)
├─ Secrets Check (Gitleaks)
└─ Dependency Review

Merge to Main
├─ All PR checks
├─ E2E Tests
├─ Sign Images (Cosign)
├─ Generate Provenance
└─ Push signed artifacts + SBOMs

Release Event
├─ Tag-based builds
├─ Attach SBOMs to GitHub release
├─ Publish to OLM catalog
└─ Security scan report artifact
```

## Part 2: AI-Assisted Security Layer

### 2.1 Architecture

**Hybrid Approach:** Traditional tools for deterministic checks, LLMs for contextual analysis and developer assistance.

**Integration Pattern:**
```
Deterministic Tools → Findings → LLM Analysis → Prioritized/Contextualized Results → Developer
```

### 2.2 LLM-Based Code Review

**GitHub Action: Claude Security Review**
- Use Anthropic's `claude-code-security-review` action
- Trigger: PRs modifying *.go files, Dockerfiles, Kustomize configs
- Analysis depth:
  - Operator-specific vulnerability patterns (RBAC misconfig, CRD validation gaps)
  - Kubernetes security contexts
  - Authentication/authorization logic
  - Secret handling in controllers
  - Input validation on custom resources
- Output: PR comments with severity, fix suggestions, CWE mappings

**Complementary: GitHub Copilot Code Review** (if available)
- Combines GPT-4 + CodeQL findings
- Provides inline suggestions during code review
- Integrates with existing SARIF uploads

### 2.3 Interactive Security Assistant

**Local CLI Tool: `security-assistant`**
- Wraps LLM API (Claude, GPT-4) with security-focused prompts
- Commands:
  ```bash
  security-assistant review <file>          # Review single file
  security-assistant explain <cve-id>       # Explain CVE impact on codebase
  security-assistant fix <issue-id>         # Generate fix for scanner finding
  security-assistant threat-model <component> # Generate threat model
  ```
- Context injection: Include relevant CRD definitions, RBAC policies, deployment configs
- Output: Markdown reports with actionable items

**Use cases:**
- Onboarding: Explain security patterns in existing code
- Triage: Prioritize scanner findings by business impact
- Remediation: Generate patches for common vulnerability patterns
- Design: Review architecture changes for security implications

### 2.4 LLM-Enhanced Triage

**Scanner Result Processor**
- Aggregate findings from gosec, Trivy, Grype, kube-linter
- Feed to LLM with context:
  - Component purpose (from code comments, READMEs)
  - Deployment architecture (from Kustomize manifests)
  - Attack surface (exposed services, RBAC permissions)
- LLM generates:
  - Risk score (adjusted for operator context)
  - Exploitability assessment
  - Remediation priority
  - Related findings clustering

**False Positive Reduction**
- LLM analyzes flagged code with control flow context
- Identifies sanitization functions, validation logic
- Suggests baseline suppressions with justifications

### 2.5 Continuous Security Knowledge Base

**Documentation Generator**
- LLM analyzes security-relevant code changes over time
- Generates:
  - Security design decisions log
  - Threat model updates
  - Security testing guidelines
  - Incident response playbooks for operator-specific scenarios

**Training Corpus**
- Build repository-specific examples:
  - Past vulnerabilities and fixes
  - Code review comments on security issues
  - Operator security best practices (Kubebuilder patterns)
- Fine-tune prompts or use RAG for improved accuracy

### 2.6 AI Tooling Recommendations

**Tier 1: Immediate (free/OSS)**
- Claude Code Security Review GitHub Action
- PR-Agent (multi-model, open-source)
- Local Claude API integration for developer CLI

**Tier 2: Enhanced (paid/enterprise)**
- GitHub Copilot Code Review (if GH Enterprise license)
- CodeRabbit Pro (Claude + GPT-4 + CodeQL integration)
- Bito AI Code Review Agent

**Tier 3: Advanced (custom)**
- Fine-tuned model on operator security patterns
- RAG system with Kubernetes CVE database + operator docs
- Automated patch generation pipeline

## Conclusion

This plan provides a layered security approach:

**Layer 1 (Deterministic):** Traditional SAST, container scanning, dependency management, SBOM generation

**Layer 2 (AI-Assisted):** LLM-based code review, intelligent triage, context-aware analysis

**Layer 3 (Process):** Developer workflows, CI/CD enforcement, continuous monitoring

**Key Differentiators:**
- Unified developer interface via Makefile targets
- Supply chain transparency with SBOMs and signing
- AI layer reduces false positives and accelerates remediation
- Red Hat/OpenShift ecosystem alignment

The toolbox is designed to run locally (`make security`) and in CI with minimal configuration overhead. AI components supplement, not replace, deterministic tools.
